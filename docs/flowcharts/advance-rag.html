3加权 RRF 融合fusion.py
score(d) = Σ 1 / (rrf_k + rank) × 通道权重，rrf_k 默认 60。
通道权重 rag_channel_weights
图谱 1.3 · FAQ 1.2 · 长文档 1.0
FAQ 高是因为人工维护更权威；图谱高是因为它只在问题提到具体实体时才有输出，一命中含金量最高
关闭融合时的兜底 _simple_merge
图谱 → 向量 → 关键词顺序直接拼接，不做 RRF 排序；关键词分 ×0.01 缩放到 0~1 区间
为什么用 RRF 而不直接加分数：向量分是 0~1 的余弦相似度，关键词分是 BM25 整数，量纲根本不同；RRF 只用排名，天然统一量纲，且高排名贡献大、低排名趋近于 0，鲁棒性好。

4重排序（二次排序）reranker.py / cross_encoder_reranker.py
模式由 rag_rerank_mode 决定，三选一：
规则级（零成本）
RRF 分归一化 ×0.4
+ 向量最高相似度 ×0.3
+ 关键词最高分归一化 ×0.15
+ 来源类型加成 ×0.1
+ 标题匹配加分 ×0.05
语意级 Cross-Encoder
取候选前 rag_rerank_candidate_limit（默认 10）条，构造「问题 + 编号候选」，让大模型输出每条的 0~1 相关性分再重排。
更准，但每次检索多一次大模型调用
off
不做二次排序，直接采用融合结果
为什么需要重排序：RRF 只用排名、丢掉了分数的绝对值 —— 两条都是第 1 名，一个相似度 0.9、一个 0.4，RRF 给的贡献却一样。

5Self-RAG 相关性过滤（可选）ai_service.self_rag_filter_relevance()
前 top_k × 2 条候选送大模型逐条打 1~5 分，丢弃 ≤ 阈值（ai_self_rag_relevance_threshold，默认 3）的片段，按新分重排。
三路来源的文本载体不同，都要认出来：
FAQ → 问：… 答：…
文档 → chunk.content
图谱 → graph_doc.content
漏认任何一路，该路候选会被当成「空文本」跳过打分，随后被过滤后的集合排除 —— 图谱事实就是这样被无声丢掉的。
Self-RAG 另有两个反思点：检索前 self_rag_should_retrieve() 判断「这问题需要查库吗」；生成后 self_rag_verify_answer() 核验答案是否被上下文支撑。

7生成ai_service.chat() → 千问
上下文文本回到 build_system_prompt()，排在【平台资料】之前注入系统提示词，连同历史对话一起发给大模型。
顺序刻意如此：平台资料有八九十行固定配置，检索结果排在它后面会被长文淹没、模型经常直接忽略 —— 而那一块才是本轮提问的答案，越靠前注意力越强。
返回：AiChatResponse(reply, conversation_id, remaining_today)
配套 · 可观测与调试（前端「RAG 调试」页）
每次提问都会回填一份调试快照，用于定位「到底哪一环没召回」：
字段含义
module_switches本轮七个模块的开关快照（含重排序实际生效模式）
all_queries / per_query_results查询变体清单，以及每个变体在关键词、向量两通道各自命中了什么、分数多少
graph_hits图谱这一路单独列一段（它不对应任何查询变体）
fused_keys / reranked_keys融合前后各取前 20 条，可逐条对比 RRF 分与重排序综合分
semantic_rerank_scores语意级重排序时，每个候选的模型相关性分
self_rag_relevance_filtered被相关性过滤丢掉了多少条
vector_error向量通道异常文本（异常不中断问答，只记录）
injected_items / injected_chars最终真正注入提示词的条数与字符数
